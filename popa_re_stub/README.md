# Реверс `popa hackvshack.net.dll`

## Вердикт
Это **не .NET-сборка**, несмотря на имя. Файл — нативный PE32+ (x64)
загрузчик-протектор (37,9 МБ). Исходников в привычном виде внутри нет:
основной код лежит в зашифрованном/виртуализованном виде. Ниже — что
удалось извлечь статически и как получить остальное.

## Структура
1. **Внешний стаб** (этот файл): `.text` всего ~12 КБ, полностью
   дизассемблирован и реконструирован в C — см. `stub/`.
2. **Ресурс `GOVNO/101`** (31,2 МБ) — вложенная DLL `payload/popa_payload.dll`
   (валидный PE32+, извлечена как есть). Отладочный путь внутри:
   `C:\Users\user\source\repos\popa\x64\Release\popa.pdb`.
3. В пейлоаде секции `.text`, `.rdata`, `.data` имеют **нулевой RawSize**
   (нули), а тело лежит в секции `.E-&` (12 МБ) в виде ~80 000 чанков
   по 31 байт с шагом 32 — кастомная виртуализация/шифрация.
4. **VEH-редирект**: пейлоад содержит абсолютные адреса функций Windows
   с машины разработчика. Стаб резолвит ~123 000 экспортов
   (kernel32 + FFmpeg/GLib/FreeType/V8 — т.е. цель на Chromium/V8,
   похоже на CS2/Panorama), строит FNV-1a хеш-мапу «захардкоженный адрес →
   реальный» и VEH-обработчиком подменяет RIP при execute-AV.

## Что в файлах
- `payload/popa_payload.dll` — извлечённый вложенный образ (сырой дамп ресурса).
- `stub/disasm/stub_full_annotated.asm` — дизасм `.text` стаба с именами импортов.
- `stub/src/*.c` — реконструкция лоадера: DllMain, поток-загрузчик,
  VEH-редирект, пост-загрузочные патчи.
- `analysis/strings_filtered.txt` — отфильтрованные строки.

## Как достать код пейлоада (статически не восстановить)
Код пейлоада материализуется только в памяти работающего процесса:
1. Windows + x64dbg: подгрузить DLL (rundll32/инжектор), дойти до
   `VirtualAlloc(0x279e8000000)` + `memcpy`, затем до вызова EP пейлоада.
2. Дампить регион `0x279e8000000` после инициализации пейлоада,
   склеить секции (Scylla / ручной маппинг, file offset == RVA).
3. VEH-таблицу адресов экспортировать скриптом (хеш-мапа в .data стаба)
   и пропатчить все захардкоженные call/jmp в дампе — иначе дизасм будет
   «прыгать в никуда».
4. Дальше — Ghidra/IDA по дампу. Чанки `.E-&` потребуют отдельного
   анализа (вероятно виртуализованные блоки кода).
